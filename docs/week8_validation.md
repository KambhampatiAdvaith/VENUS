This runbook documents how to validate the four major V.E.N.U.S. workflows
end-to-end and collect evidence for final project sign-off.  No production
behavior is changed by following these steps.

## 1. System prerequisites

Before running any workflow validation, ensure the backend is reachable and
healthy.

### Start the backend (Windows PowerShell)

```powershell
cd backend
.\venv\Scripts\Activate.ps1
$env:ENABLE_STARTUP_TELEMETRY_SIMULATOR="true"
$env:ENABLE_AI_PREDICTION_LOOP="true"
$env:ENABLE_KAFKA_TELEMETRY_CONSUMER="false"
$env:ENABLE_KAFKA_FAULT_CONSUMER="false"
python -m uvicorn backend.api.main:app --reload
```

To capture structured logs at the same time:

```powershell
python -m uvicorn backend.api.main:app --reload 2>&1 | Tee-Object -FilePath .\backend.log
```

### Verify the backend is healthy

```powershell
(Invoke-WebRequest http://127.0.0.1:8000/health).Content
```

Expected response:

```json
{"status":"healthy","database":"connected"}
```

### Start the frontend (separate terminal)

```powershell
cd frontend
npm run dev
```

Open `http://localhost:3000` in a browser.

## 2. Workflow 1 — Normal telemetry flow

**Pipeline:**
```
Substation Simulator -> Edge Isolation Forest -> MQTT -> Kafka
  -> Kafka Consumer -> PostgreSQL -> FastAPI -> WebSocket -> Dashboard
```

### Purpose

Validate that telemetry generated by the substation simulator travels through
the full edge-cloud pipeline, is stored in PostgreSQL, is served by FastAPI,
and appears on the live dashboard with correct freshness indicators.

### Preconditions

- Backend is running and `/health` returns `"database":"connected"`.
- Frontend dashboard is open at `http://localhost:3000`.
- At least one of the following is true:
  - `$env:ENABLE_STARTUP_TELEMETRY_SIMULATOR="true"` was set before startup, **or**
  - Kafka consumers are enabled and a real MQTT/Kafka pipeline is available.

### Step-by-step validation procedure

**Step 1 — Confirm telemetry exists in the database**

```powershell
(Invoke-WebRequest http://127.0.0.1:8000/telemetry/latest).Content
```

Expected: a JSON object containing `substation_id`, `voltage`, `current`,
`temperature`, `load`, `frequency`, and timestamp fields
(`generated_at`, `database_written_at`).

**Step 2 — Confirm the latency endpoint reports reasonable values**

```powershell
(Invoke-WebRequest http://127.0.0.1:8000/telemetry/latency).Content
```

Expected: a JSON object with `avg_latency_ms`, `min_latency_ms`,
`max_latency_ms`, `median_latency_ms`, and `sample_count > 0`.

**Step 3 — Confirm the telemetry list endpoint returns rows**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/telemetry?limit=5").Content
```

Expected: a JSON array with at least one telemetry object.

**Step 4 — Verify dashboard shows live telemetry**

Open `http://localhost:3000` and navigate to the Telemetry page.  Confirm that:

- Telemetry rows appear in the table.
- The "last updated" or freshness indicator shows a recent timestamp
  (within the last few minutes).
- The live-update banner (if visible) shows the WebSocket is connected.

**Step 5 — Trigger manual telemetry if the dashboard is empty**

```powershell
Invoke-RestMethod -Method Post http://127.0.0.1:8000/telemetry/simulate/normal
```

Wait five seconds, then refresh the dashboard.

**Step 6 — Confirm WebSocket live updates**

Keep the dashboard open.  In a second PowerShell terminal, trigger another
simulation cycle:

```powershell
Invoke-RestMethod -Method Post http://127.0.0.1:8000/telemetry/simulate/normal
```

Observe that the dashboard updates without a manual browser refresh.

### Expected evidence

- `/health` JSON response screenshot or PowerShell output.
- `/telemetry/latest` JSON response showing a fresh row.
- `/telemetry/latency` JSON response with `sample_count > 0`.
- Dashboard screenshot showing recent telemetry rows and live-update indicator.

### Troubleshooting notes

| Symptom | Likely cause | Fix |
|---|---|---|
| `/health` returns `"database":"disconnected"` | PostgreSQL not running | Start the database container or service |
| `/telemetry/latest` returns 404 or empty | No rows in DB | Trigger `POST /telemetry/simulate/normal` |
| Dashboard shows stale data | Frontend not refreshing | Check WebSocket connection; hard-refresh the browser |
| Latency `sample_count` is 0 | No telemetry rows with both timestamps | Trigger simulation and re-query after 10 s |

## 3. Workflow 2 — Fault detection flow

**Pipeline:**
```
Fault Injection -> Edge Anomaly Detection -> MQTT -> Kafka
  -> Prediction Engine -> Alert Generation -> Dashboard
```

### Purpose

Validate that an injected fault produces an anomaly detection event at the
edge layer, propagates through the pipeline, triggers a cloud-side prediction,
generates an alert, and appears on the Alerts page of the dashboard.

### Preconditions

- Backend is running and healthy.
- At least one normal telemetry row exists (complete Workflow 1 first if needed).
- Frontend Alerts page is open.

### Step-by-step validation procedure

**Step 1 — Inject a fault event**

```powershell
Invoke-RestMethod -Method Post http://127.0.0.1:8000/telemetry/simulate/fault
```

Expected: HTTP 200 with a confirmation body, or the endpoint returns the
created row.

**Step 2 — Confirm fault telemetry row is stored**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/telemetry?limit=5").Content
```

Look for a row where `edge_anomaly` is `true` or `edge_anomaly_score` is above
the normal baseline.

**Step 3 — Trigger the prediction engine**

```powershell
Invoke-RestMethod -Method Post http://127.0.0.1:8000/predictions/run
```

**Step 4 — Confirm a prediction record was created**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/predictions?limit=5").Content
```

Expected: at least one row where `predicted_fault` is `true` or
`probability` is above 0.5.

**Step 5 — Confirm faults are visible in the faults endpoint**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/faults?limit=5").Content
```

Expected: a list of recent fault events associated with the injected anomaly.

**Step 6 — Verify alerts appear on the dashboard**

Open the Alerts page at `http://localhost:3000` and confirm that new alert
rows appear with the injected fault data.

**Step 7 — Confirm alert timestamps are recent**

Alert rows should have a timestamp within the last few minutes, matching the
simulation time.

### Expected evidence

- `POST /telemetry/simulate/fault` success response.
- Telemetry row with anomaly flag visible in `/telemetry` output.
- Prediction row with `predicted_fault: true` or high `probability`.
- Dashboard Alerts page screenshot showing the new alert.

### Troubleshooting notes

| Symptom | Likely cause | Fix |
|---|---|---|
| No fault row in `/telemetry` | Simulation failed | Check backend logs; retry the POST |
| No prediction after `/predictions/run` | Prediction loop disabled or no eligible rows | Ensure `ENABLE_AI_PREDICTION_LOOP=true` or call `POST /predictions/run` |
| Alerts page is empty | No faults written to the faults table | Verify `/faults` endpoint directly; check DB write in logs |

## 4. Workflow 3 — Autonomous load balancing

**Pipeline:**
```
High Load -> Risk Prediction -> Recommendation Created
  -> Operator Approval -> Execution -> Balancing History -> Decision Audit Trail
```

### Purpose

Validate the full autonomous load balancing loop: a high-load scenario triggers
a recommendation, an operator approves it, the system executes it, and the
outcome is recorded in balancing history and the decision audit trail.

### Preconditions

- Backend is running and healthy.
- A prediction with elevated risk exists (complete Workflows 1 and 2 first, or
  generate predictions that trigger load balancing).
- Frontend is open to the Recommendations or Load Balancing page.

### Step-by-step validation procedure

**Step 1 — Confirm a recommendation exists**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/load-balancing?limit=5").Content
```

Expected: a list of recommendations, at least one with `status` of `"pending"`
or `"recommended"`.

If no recommendations exist, trigger a high-load simulation and run predictions:

```powershell
Invoke-RestMethod -Method Post http://127.0.0.1:8000/telemetry/simulate/fault
Invoke-RestMethod -Method Post http://127.0.0.1:8000/predictions/run
```

Then re-check `/load-balancing`.

**Step 2 — Note the recommendation ID**

From the JSON output, copy the `id` field of a pending recommendation.

**Step 3 — Approve the recommendation**

Replace `<id>` with the actual recommendation ID:

```powershell
Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8000/load-balancing/<id>/approve" `
  -ContentType "application/json"
```

Expected: the response shows the recommendation status is now `"approved"` or
`"executed"`.

**Step 4 — Confirm execution in load-balancing history**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/load-balancing?limit=5").Content
```

The previously pending recommendation should now have `status` of `"approved"`,
`"executed"`, or `"completed"`.

**Step 5 — Verify the decision audit trail**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/load-balancing/history?limit=5").Content
```

Expected: a balancing history record that references the approved
recommendation, including `action`, `timestamp`, and outcome fields.

**Step 6 — Verify on the dashboard**

Open `http://localhost:3000` and navigate to:

- **Load Balancing** page — confirm the recommendation status is updated.
- **Balancing History** page — confirm the execution is listed.
- **Decision Audit Trail** page — confirm the audit record with `"approved"`
  action is present.

### Expected evidence

- `/load-balancing` screenshot showing a pending recommendation.
- API response confirming approval.
- Balancing History page screenshot showing the executed action.
- Decision Audit Trail page screenshot showing the audit record.

### Troubleshooting notes

| Symptom | Likely cause | Fix |
|---|---|---|
| `/load-balancing` is empty | No predictions above risk threshold | Run fault injection + `POST /predictions/run` |
| Approval returns 404 | Wrong recommendation ID | Re-fetch `/load-balancing` and use the correct `id` |
| Status stays "pending" after approval | Execution not triggered | Check backend logs for execution errors |
| Audit trail empty | History not written | Verify the load-balancing execution route writes to history |

## 5. Workflow 4 — Recommendation rejection

**Pipeline:**
```
Reject Recommendation -> Status changes to Rejected
  -> Audit trail updated -> No execution performed
```

### Purpose

Validate that when an operator rejects a load-balancing recommendation, the
status changes to `"rejected"`, the audit trail records the rejection, and no
balancing action is executed.

### Preconditions

- Backend is running and healthy.
- At least one recommendation with `status` of `"pending"` exists (from
  Workflow 3 or by injecting another high-load event).

### Step-by-step validation procedure

**Step 1 — Obtain a pending recommendation ID**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/load-balancing?limit=10").Content
```

Copy the `id` of a recommendation with `status: "pending"`.

**Step 2 — Reject the recommendation**

Replace `<id>` with the actual recommendation ID:

```powershell
Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8000/load-balancing/<id>/reject" `
  -ContentType "application/json"
```

Expected: the response shows `status` changed to `"rejected"`.

**Step 3 — Confirm status is rejected**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/load-balancing/<id>").Content
```

Expected: `"status": "rejected"`.

**Step 4 — Confirm audit trail records the rejection**

```powershell
(Invoke-WebRequest "http://127.0.0.1:8000/load-balancing/history?limit=5").Content
```

Expected: an audit record with `action` set to `"rejected"` and no
`executed_at` or execution timestamp — confirming no balancing action was
performed.

**Step 5 — Verify no balancing action was executed**

The balancing history record for this recommendation must **not** show an
outcome or execution confirmation.  The recommendation count in the executed
load-balancing list must not have increased from Step 1.

**Step 6 — Verify on the dashboard**

Navigate to:

- **Recommendations / Load Balancing** page — the rejected recommendation must
  show `"Rejected"` status.
- **Decision Audit Trail** page — a rejection entry must appear.
- **Balancing History** page — no new execution entry should have been added for
  this recommendation.

### Expected evidence

- API response from the reject endpoint showing `"status": "rejected"`.
- `/load-balancing/history` output showing a rejection record.
- Dashboard screenshot: Recommendations page with rejected status visible.
- Dashboard screenshot: Decision Audit Trail showing rejection entry.
- Confirmation that Balancing History has no new execution for this ID.

### Troubleshooting notes

| Symptom | Likely cause | Fix |
|---|---|---|
| Reject endpoint returns 404 | Wrong ID or route not implemented | Check route definitions in backend; verify ID |
| Status stays "pending" | Reject route not persisting the update | Check backend logs for DB write errors |
| Audit trail does not show rejection | History write missing for rejections | Verify the reject route also writes a history record |

Week 7 benchmark reports cover API latency, telemetry throughput, AI
evaluation, and edge-vs-cloud comparison.  These reports do not need to be
regenerated for Week 8 unless data has changed.  Reuse the files from
`benchmark_results/` as directed in the

```powershell
  --base-url http://127.0.0.1:8000 `
  --duration 30 `
  --ai-eval `
  --edge-cloud
```

```powershell
Select-String -Path .\backend.log `
  -Pattern "backend.kafka","backend.mqtt","WARNING","ERROR"
```

```powershell
(Invoke-WebRequest http://127.0.0.1:8000/nodes).Content
```

Expected: a list of nodes with `status`, `load`, and `last_updated` fields.
